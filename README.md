# LOCORO

LOCORO は、レジャーホテル向けのリアルタイム予約・部屋状態管理システムです。

従来の宿泊予約サービスとは異なり、レジャーホテルでは「今すぐ使いたい」「空きそうな部屋を押さえたい」「清掃完了のタイミングを知りたい」といった即時性の高いニーズがあります。

LOCORO は、店舗側が部屋状態をリアルタイムに管理し、ユーザー側が空室・利用中・清掃中などの状況を確認できるようにすることで、電話確認や現地到着後の待ち時間を減らすことを目指しています。

現在は MVP（Minimum Viable Product）として開発中です。

## サービス概要

LOCORO は、レジャーホテルにおける「リアルタイムな部屋状況確認」と「短時間予約」を組み合わせた部屋管理システムです。

レジャーホテルでは、一般的なホテル予約のように数日前から部屋を予約するよりも、当日・直前・短時間で利用したいケースが多くあります。

しかし、ユーザー側からは以下のような課題があります。

- 今どの部屋が空いているか分かりにくい
- 電話で確認する手間がある
- 現地に行っても満室・清掃中の可能性がある
- 空きそうな部屋を事前に押さえにくい

店舗側にも以下のような課題があります。

- 電話対応の負担がある
- 部屋状況の案内が属人的になりやすい
- 清掃状況・空室状況をリアルタイムに伝えにくい
- 来店前のユーザー導線を作りにくい

LOCORO では、店舗スタッフが部屋状態を管理画面から更新し、ユーザー側がリアルタイムに部屋状況を確認できる仕組みを提供します。

## LOCORO独自の予約ロジック

LOCORO の特徴は、レジャーホテルの利用シーンに合わせた「様子見予約」と「30分キープ」です。

### 1. 空室の30分キープ

空室の部屋に対して、ユーザーは30分間のキープを行えます。

```text
空室
↓
ユーザーが30分キープ
↓
キープ中
↓
来店・入室
↓
利用中
```

### 2. 利用中の部屋への様子見予約

利用中の部屋に対して、ユーザーは「様子見予約」を行えます。

これは、部屋がすぐには空いていない場合でも、一定時間内に部屋が空いたら、清掃完了後に30分間キープされる仕組みです。

```text
利用中
↓
ユーザーが様子見予約
↓
予約待ち
↓
利用者が退出
↓
清掃中
↓
清掃完了
↓
30分キープ
↓
来店・入室
↓
利用中
```

### 3. 清掃中の部屋への清掃完了後キープ

清掃中の部屋に対しても、清掃完了後に30分間キープできる導線を用意しています。

```text
清掃中
↓
ユーザーが清掃完了後キープ予約
↓
清掃完了
↓
30分キープ
↓
来店・入室
↓
利用中
```

### 4. キープ期限切れ時の警告

30分キープの期限が切れた場合、店舗管理ダッシュボード上に警告を表示します。

```text
30分キープ
↓
期限切れ
↓
管理画面に要確認警告
↓
スタッフが入室状況を確認
↓
空室 または 利用中 に更新
```

これにより、店舗スタッフが期限切れの部屋を見逃しにくくし、現場運用に近い状態管理を目指しています。

## 開発背景

レジャーホテルの利用では、「今すぐ使える部屋を探す」「満室かどうかを確認する」「清掃完了を待つ」といった即時性の高い行動が多くあります。

一方で、既存の宿泊予約サービスは、数日後・数週間後の宿泊予約を前提としたものが多く、レジャーホテル特有のリアルタイムな利用導線には合いにくいと感じました。

そこで、LOCORO では以下のような価値提供を目指しています。

- ユーザーが来店前に部屋状況を確認できる
- 空室・利用中・清掃中をリアルタイムに見られる
- 空きそうな部屋を短時間キープできる
- 店舗側の電話対応や案内負担を減らす
- レジャーホテル特有の運用に合った予約導線を作る

## 技術的に工夫した点

### 1. レジャーホテル特有の状態管理

一般的なホテル予約とは異なり、レジャーホテルでは「利用中」「清掃中」「空室」などのリアルタイムな状態管理が重要になります。

LOCORO では、部屋の状態と予約状態を分けて管理し、現場運用に近い予約フローを表現しています。

### 2. 様子見予約と30分キープ

利用中の部屋に対して、ユーザーが事前に様子見予約できる仕組みを実装しています。

一定時間内に部屋が空いた場合、清掃完了後に30分間キープすることで、ユーザーが来店しやすい導線を目指しています。

### 3. 店舗スタッフごとのホテル制御

HotelStaff モデルで、ログインユーザーと所属ホテルを紐づけています。

これにより、店舗スタッフが自分の所属ホテルの部屋だけを管理できる構成を目指しています。

### 4. views.py の責務分離

機能が増えるにつれて views.py が肥大化したため、以下のように責務ごとにファイルを分割しました。

```text
customer_views.py
manager_views.py
reservation_views.py
```

これにより、客側表示、店舗側管理、予約処理を分けて管理しやすくしています。

### 5. JavaScript fetch による非同期ステータス更新

店舗管理ダッシュボードでは、JavaScript の fetch を利用して部屋ステータスを非同期で更新しています。

これにより、スタッフが部屋カードを選択し、画面遷移を最小限にしながら状態変更できるUIを目指しています。

### 6. 本番環境とローカル環境のDB切り替え

環境変数 `DATABASE_URL` の有無で使用するDBを切り替えています。

- `DATABASE_URL` がある場合: PostgreSQL
- `DATABASE_URL` がない場合: SQLite

これにより、ローカルでは軽く開発し、本番では PostgreSQL を使う構成にしています。

### 7. Cloudinaryによる画像永続化

Django の ImageField の保存先を Cloudinary に変更し、Render の再デプロイ後も画像が消えにくい構成にしています。

### 8. Ruff によるコード品質チェック

未使用importや不要な変数、import順などを検出するために Ruff を導入しています。

```bash
docker compose exec web ruff check .
```

Django の動作確認だけでなく、コード品質も確認できるようにしています。

### 9. GitHub PRベースの開発

一人開発でも、Issue 作成 → ブランチ作成 → 実装 → Pull Request → マージ の流れを意識しています。

変更理由や作業履歴を残すことで、後から振り返りやすい開発フローを目指しています。

## ローカル開発環境のセットアップ

### 1. リポジトリをクローン

```bash
git clone https://github.com/Hibiki0417/LOCORO.git
cd LOCORO
```

### 2. `.env` を作成

プロジェクト直下に `.env` を作成します。

ローカルで SQLite を使う場合は、DB接続用の環境変数を空にして起動できます。

画像アップロードを Cloudinary で確認する場合は、Cloudinary の接続情報を設定します。

### 3. Dockerで起動

```bash
docker compose build
docker compose up -d
```

### 4. マイグレーション実行

```bash
docker compose exec web python manage.py migrate
```

### 5. 管理ユーザー作成

```bash
docker compose exec web python manage.py createsuperuser
```

### 6. 開発サーバー確認

```text
http://localhost:8000/hotels/
```
